A JOSE signature algorithm (RFC 7518 §3.1), and the one RFC 8037 adds.

none is not here and never will be. It is the algorithm that made "verified" mean "not verified" in a dozen libraries, and a type that cannot express it cannot be talked into accepting it.

typeClock
pub(all) enum Clock {
  At(Int64)
  Ignored
} derive(Eq, @debug.Debug)

When the time claims are measured against.

A library has no clock — reading one is a side effect and there is no reason for a token verifier to have that power — so the instant comes in from the caller. Ignored is the way to read a token without asking whether it has expired: a debugging tool, an audit of tokens already collected, a migration that has to read what was issued last year. It is spelled out at the call site because the alternative is a verifier that quietly stopped checking.

typeKeyed
type Keyed

A keyed MAC, standing in as both signer and verifier.

HMAC is symmetric: the same key that signs verifies. What it is not is a signature — anyone who can check an HS256 token can mint one — so a token verified this way says only that someone holding the shared secret issued it.

implements @spec.Signer, @spec.Verifier
typeOnClash
pub(all) enum OnClash[T] {
  Ignore
  Panic
  Handle((T, T) -> T)
}

What to do when a setting is given twice.

Handle receives the base and the merged result and returns whichever it wants, so a caller can audit, refuse, or merge some other way entirely.

There is no Warn: a library has nowhere to warn to. It arrives when moonlog does.

typePolicy
pub(all) struct Policy {
  leeway : Int64
  expiry : Bool
  not_before : Bool
  issued_at : Bool
  issuer : String?
  audience : Array[String]
  subject : String?
  typ : String?
  required : Array[String]
} derive(Eq, @debug.Debug)

What a token has to satisfy beyond its signature.

Every field is a check that is either off or told what to expect, and every default is what the mainstream libraries do: exp and nbf are checked, iat is not, and iss, aud, sub and the header's typ are looked at only when the caller says what to expect. Nothing is enforced implicitly and nothing is skipped implicitly.

One of these is assembled once for a deployment and passed to every verification, which is what jsonwebtoken's Validation, .NET's TokenValidationParameters and jose's options object are for.

typeWins
pub(all) enum Wins {
  Base
  Extra
} derive(Eq, @debug.Debug)

Which side wins when a setting is given twice.

Every function here that takes both a base and something layered over it says which one wins, and lets a caller say otherwise. The defaults differ by function and each one says why: verify lets the override win, because a per-call argument is more specific than a policy assembled once; sign lets the base win, because the header it computes describes the signature it is about to make.

fnsign
pub fn sign(Map[String, Json], Alg, &@spec.Signer, typ? : String?, extra? : Map[String, Json], wins? : Wins, clash? : OnClash[Map[String, Json]]) -> String

Sign a claims set as a compact JWT.

extra goes into the header beside alg and typ — kid is what it is usually for, so a verifier can pick the right key out of a set before it verifies anything.

typ is "JWT", which is what every library writes and what RFC 7519 §5.1 recommends. None leaves it out; another string puts that in — RFC 9068's access tokens want "at+jwt".

**extra cannot quietly rewrite alg or typ.** The header describes the signature this function is about to make; a token whose header says none while the bytes say HS256 is not a configuration choice, it is a mistake, so wins starts at Base and clash at Panic. A caller who means it can say wins=Extra, clash=Ignore.

The key is whatever can sign; this package never chooses an algorithm's implementation, so a program that issues only HS256 tokens links only HMAC.

fnverify
pub fn verify(StringView, Alg, &@spec.Verifier, now~ : Clock, policy? : Policy, wins? : Wins, clash? : OnClash[Policy], leeway? : Int64, expiry? : Bool, issuer? : String, audience? : Array[String]) -> Map[String, Json] raise Refused

Verify a compact JWT and return its claims.

**The algorithm is the caller's, not the token's.** A verifier that reads alg out of the header and then trusts it is how an RS256 public key gets used as an HS256 shared secret, and how none gets accepted; here the header must match what the caller already decided, or the token is refused.

The signature is checked before any claim is read, so a forged token is never inspected for its contents.

Configuration has three layers, each overriding the one before: @jwt.policy < the policy given here < the named arguments given here. wins turns the last two around; clash decides whether being given a setting twice is silent, fatal, or yours to arbitrate.

now is not configuration but data: the instant the time claims are measured against, or Ignored to read a token without asking whether it has expired — a debugging tool, an audit of tokens already collected, a migration that has to read what was issued last year.

pub fn Set::pick(Self, alg~ : String, id? : String, usage? : String?, first? : Bool) -> Jwk?

The key to verify a token with: the one named by kid if the token names one, otherwise the only candidate for this algorithm.

A key that says nothing about its algorithm is a candidate for any; one that names a different algorithm, or is marked for encryption, is not. When several remain, none is returned — picking one arbitrarily is how a rotated key silently keeps verifying — and first is how a caller asks for the other behaviour.

usage is the use a candidate must carry when it carries one; "sig" is the default because this is a signature library. None accepts any.

fndecrypt
pub fn decrypt(StringView, key~ : Identity, alg~ : Alg, enc~ : Enc) -> Bytes raise Refused

Open a token, checking that the header names the algorithms the caller expects.

The expected alg and enc are arguments and not read from the header on the caller's behalf for the reason JWT's none exists: a recipient that believes whatever the token says about itself can be talked into the weakest algorithm it supports. A token that names another algorithm is Malformed rather than opened under the caller's.

fnencrypt
pub fn encrypt(BytesView, key~ : Key, alg~ : Alg, enc~ : Enc, cek? : Bytes?, iv~ : BytesView, seed? : BytesView) -> String raise Refused

Seal a payload under a key, into the compact serialisation: five base64url parts, the header first, so the recipient knows what to do before it does anything.

cek is the content-encryption key and iv the nonce; both are the caller's, for the reason this library has no generator. Under dir the CEK is the shared key and cek must be None; under any other algorithm it is required and must be cek_size octets. seed is what RSA-OAEP-256 needs to make its padding: the algorithm is randomised, and the randomness has to come from somewhere that is not here.

fnunwrap
pub fn unwrap(BytesView, BytesView) -> Bytes raise Refused

The inverse: recover the key, or Malformed when the octets are not a wrapped key under this one. The integrity check is the initial value coming back out of the last round — that is the whole reason the algorithm mixes a counter into it.

fnwrap
pub fn wrap(BytesView, BytesView) -> Bytes raise Refused

Wrap a content-encryption key under a key-encryption key. The plaintext must be a whole number of eight-octet blocks and at least sixteen octets, which is what every CEK in RFC 7518 is.

Mooncred@tokenv

token

Signed tokens: HMAC over the caller's own octets, in a string a URL or a cookie can carry.

The shape is itsdangerous': a base64url payload, a base64url timestamp, and a base64url tag, separated by dots. What keeps two uses of one key apart is the salt, which is hashed into the tag and never travels with it, so a token signed for one purpose cannot be replayed against another even though the key is the same.

pub fn dns_match(String, String) -> Bool

Whether the dNSName pattern names host (RFC 6125 §6.4.3): label by label, ASCII case insensitive. A first label of exactly * stands for one whole label and needs two more after it, so *.a.example covers b.a.example and neither a.example nor c.b.a.example, and *.com covers nothing. fnverify
pub fn verify(ArrayView[Bytes], Roots, now~ : Int64, host? : String, policy? : Policy) -> Array[Cert] raise Refused

Validate a chain and return the path found: the leaf, the intermediates it runs through, and the anchor it ends on.

chain is the leaf followed by the intermediates the peer sent, in any order; ones the path does not need are ignored, which is what a TLS server's habit of sending a cross-signed extra asks for. now is the time to judge validity at, in seconds since the Unix epoch. host, when given, is a DNS name or an IP literal the leaf must name; without it names are not compared.

The rules, and whose they are: - Names come from subjectAltName only, never the commonName (RFC 6125, Go since 1.15, webpki). - Every issuer must be a CA, have keyCertSign when it lists key usages, and respect its pathLenConstraint. A leaf that is a CA is refused, as webpki does. - Validity is checked on every certificate but the anchor. - The leaf must allow policy.usage; an issuer that lists key purposes must allow it too (Go and the Mozilla root programme chain the restriction). - An unknown critical extension anywhere on the path refuses it. - Name constraints bind dNSName, iPAddress, rfc822Name, directoryName and the host of a URI; a constraint of another form, over a name of that form, refuses rather than guesses. - Several candidate issuers with the issuer's name are each tried, preferring the one whose subjectKeyIdentifier matches the authorityKeyIdentifier; every signature check spends from policy.budget.

When no path works, the refusal is the first reason a candidate path failed, or Issuer when there was no candidate at all.
